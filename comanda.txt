# COMANDA DE DESENVOLVIMENTO — AV2 GREENCODE

## Objetivo geral

Você é um agente de desenvolvimento responsável por evoluir o projeto existente Greencode para atender à segunda atividade avaliativa (AV2).

O projeto anterior funciona por meio de uma aplicação de terminal (CLI) e utiliza arquivos criptografados para armazenar dados. A nova versão deverá utilizar um servidor HTTP, uma API REST, um banco de dados relacional PostgreSQL e o Prisma ORM.

O desenvolvimento deverá ser realizado diretamente nos arquivos do projeto existente, preservando as regras de negócio, os modelos, as validações e as funcionalidades que já estejam implementadas e sejam compatíveis com a nova arquitetura.

**Trabalhe seguindo rigorosamente as etapas abaixo, na ordem estabelecida. Não tente implementar todo o sistema de uma só vez.**

Ao concluir cada etapa, execute as verificações correspondentes, corrija os problemas encontrados e só avance quando os critérios de conclusão daquela etapa forem atendidos.

# FASE 1 — ANÁLISE E PLANEJAMENTO

## Passo 1 — Analisar o projeto original

Antes de escrever ou alterar código, examine o projeto existente.

Identifique:

- A linguagem de programação e as tecnologias utilizadas.
- A estrutura de diretórios e arquivos.
- Os modelos de domínio e seus atributos.
- As regras de negócio e os cálculos existentes.
- As validações e as transições de status dos equipamentos.
- O funcionamento da autenticação, incluindo hash de senhas, sessões e permissões.
- A forma como os dados são armazenados nos arquivos criptografados.
- Os relacionamentos entre as entidades.
- Os testes existentes e os cenários de validação.
- As dependências e os comandos necessários para executar o sistema.

Não presuma que os nomes, atributos ou comportamentos das entidades são iguais aos de outros projetos. Utilize o código existente como fonte principal.

### Ao concluir o passo 1

Apresente um diagnóstico resumido com:
1. Como o projeto funciona atualmente.
2. Quais funcionalidades já existem.
3. O que poderá ser reaproveitado.
4. O que precisa ser modificado.
5. Quais informações ainda estão ausentes ou precisam de confirmação.

Não modifique arquivos sem necessidade durante esta análise.

## Passo 2 — Definir a arquitetura da nova versão

Com base na análise anterior, determine como o projeto será reorganizado.

A arquitetura deverá seguir o padrão Controller-Service-Repository.

Responsabilidades:

- Controllers: recebem requisições HTTP e retornam respostas.
- Services: executam as regras de negócio e coordenam operações.
- Repositories: acessam o banco de dados por meio do Prisma.
- Routes: definem os endpoints da API.
- Middlewares ou hooks: tratam autenticação, autorização e outras verificações compartilhadas.
- Schemas: definem as estruturas e validações dos dados recebidos.

A estrutura sugerida é:

src/
- controllers/
- services/
- repositories/
- routes/
- middlewares/
- schemas/
- utils/
- config/
- app.ts
- server.ts

prisma/
- schema.prisma
- seed.ts

tests/

Adapte essa organização à estrutura existente sempre que isso evitar alterações desnecessárias.

Utilize Node.js e TypeScript. Para o servidor HTTP, prefira Fastify, recomendado pelo professor. O Express é uma alternativa permitida caso exista uma justificativa concreta para escolhê-lo.

### Ao concluir o passo 2

Defina a estrutura que será utilizada, identifique as dependências necessárias e estabeleça uma ordem de implementação.

Não implemente ainda todas as funcionalidades. Primeiro estabeleça uma base arquitetural coerente.

# FASE 3 — BANCO DE DADOS

## Passo 4 — Configurar o PostgreSQL e o Prisma

Configure a conexão com o PostgreSQL e prepare o Prisma ORM.

Utilize variáveis de ambiente para configurar a conexão com o banco.

Em seguida:

1. Configure o Prisma conforme a versão instalada e a estrutura do projeto.
2. Configure o arquivo `schema.prisma`.
3. Defina os modelos e seus relacionamentos.
4. Configure o acesso ao banco de dados pelo Prisma Client.
5. Prepare os comandos de migração.

O professor recomenda o PostgreSQL e solicita a utilização do Prisma ORM.

Não comece a implementar todas as rotas antes de confirmar que a conexão com o banco funciona.

## Passo 5 — Criar os modelos e relacionamentos

O enunciado da AV2 identifica cinco entidades:

- `Organizacao`
- `Contrato`
- `Lote`
- `Equipamento`
- `Movimentacao`

Utilize os modelos e atributos encontrados no projeto original para definir os campos correspondentes.

Respeite os relacionamentos exigidos pelo professor:

- Uma organização pode possuir um contrato opcional e vários lotes.
- Um lote pode possuir vários equipamentos.
- Um equipamento pode possuir várias movimentações.

Configure as chaves primárias, as chaves estrangeiras, a opcionalidade dos relacionamentos e as restrições necessárias.

Também configure as restrições de unicidade para CNPJ e código de barras interno, conforme os campos existentes no domínio.

Não invente atributos ou relacionamentos sem justificativa.

## Passo 6 — Criar e validar as migrações

Gere a primeira migração do banco de dados e aplique-a no ambiente de desenvolvimento.

Verifique:

- Se todas as tabelas foram criadas.
- Se os campos possuem os tipos corretos.
- Se os relacionamentos funcionam.
- Se as chaves estrangeiras foram configuradas.
- Se as restrições de unicidade funcionam.
- Se o Prisma consegue consultar e inserir dados.

Não utilize comandos que apaguem o banco ou os dados existentes sem autorização explícita.

### Critério para avançar

Só prossiga quando o banco estiver acessível, o esquema estiver aplicado e os modelos puderem ser utilizados pelo Prisma.

- Possuir tratamento centralizado de erros.

Implemente inicialmente uma rota simples de verificação de funcionamento, como um endpoint de saúde da aplicação.

Não implemente ainda todas as funcionalidades de negócio.

## Passo 8 — Validar o servidor e o banco em conjunto

Execute o servidor e confirme que ele consegue utilizar o Prisma para consultar o PostgreSQL.

Teste:

1. Inicialização do servidor.
2. Acesso à rota de verificação.
3. Conexão com o banco.
4. Tratamento de falhas de conexão.
5. Respostas HTTP.
6. Encerramento correto do processo.

# FASE 5 — CAMADA DE DADOS E REGRAS DE NEGÓCIO

## Passo 9 — Implementar os repositories

Implemente os repositories para centralizar o acesso ao PostgreSQL por meio do Prisma.

Crie apenas os necessários para as entidades e operações existentes.

Cada repository deverá conter as operações de persistência necessárias, como:

- Consultar registros.
- Buscar registros por identificador.
- Criar registros.
- Atualizar registros.
- Excluir registros quando permitido.
- Consultar relacionamentos.

Os repositories não devem concentrar as regras de negócio.

## Passo 10 — Adaptar os services existentes

Reaproveite as regras de negócio da aplicação anterior e adapte-as para trabalhar com os novos repositories.

Preserve:

- Validações.
- Cálculos financeiros.
- Regras de transição de status.
- Restrições de negócio.
- Regras de autorização que já existam.
- Comportamentos necessários para o funcionamento das entidades.

Se a lógica estiver diretamente vinculada aos arquivos criptografados, refatore-a para utilizar a nova camada de persistência sem alterar desnecessariamente o comportamento.

Evite duplicar regras em controllers, repositories e services.

## Passo 11 — Implementar transações e concorrência

Identifique operações que envolvam várias alterações relacionadas.

Utilize transações do Prisma quando necessário.

Exemplos exigidos como referência pelo enunciado:

- Criar um lote com vários equipamentos.
- Atualizar o status de um equipamento e registrar uma movimentação.

Se uma operação falhar, as alterações relacionadas deverão ser revertidas quando fizerem parte da mesma transação.

Avalie também o versionamento otimista sugerido pelo professor. Se implementado, o sistema deverá detectar conflitos de atualização, e não apenas armazenar um número de versão.

Não introduza complexidade desnecessária: implemente esses mecanismos de acordo com as operações reais do sistema.

### Critério para avançar

Teste os services e repositories antes de expô-los pela API.

Verifique se as regras de negócio continuam corretas e se as transações mantêm a consistência dos dados.

# FASE 6 — API REST

## Passo 12 — Criar as rotas da API

Com o banco e os services funcionando, implemente os controllers e as rotas HTTP.

Identifique as operações disponíveis no sistema original e exponha-as por meio de endpoints adequados.

- As validações.

# FASE 7 — AUTENTICAÇÃO E AUTORIZAÇÃO

## Passo 15 — Implementar o login com JWT

Adapte o mecanismo de autenticação do projeto anterior.

O fluxo esperado é:

1. O usuário envia suas credenciais.
2. O servidor localiza o usuário no banco.
3. A senha informada é comparada com o hash armazenado.
4. Se as credenciais forem válidas, o servidor gera um token JWT.
5. O token identifica o usuário e contém as informações mínimas necessárias para a autorização.
6. O cliente utiliza o token no cabeçalho `Authorization` das requisições seguintes.

Utilize o plugin `@fastify/jwt` se o projeto adotar Fastify.

Preserve o algoritmo de hash existente se ele for adequado. Não armazene senhas em texto puro.

Configure o segredo do JWT e seu prazo de validade por meio de configurações seguras.

Não invente um sistema de cadastro de usuários se isso não fizer parte do projeto ou dos requisitos identificados.

## Passo 16 — Proteger as rotas

Implemente o mecanismo responsável por verificar os tokens nas rotas protegidas.

Verifique:

- Token ausente.
- Token inválido.
- Token expirado.
- Usuário identificado.
- Permissão necessária para a operação.

Reaproveite os papéis e as permissões existentes no projeto anterior.

Autenticação e autorização são responsabilidades diferentes: estar autenticado não significa possuir permissão para executar todas as operações.

## Passo 17 — Testar a segurança

Execute testes com:

- Credenciais válidas.
- Credenciais inválidas.
- Token válido.
- Token ausente.
- Token inválido.
- Token expirado.
- Usuário sem permissão para a operação.

### Critério para avançar

O sistema deverá impedir acessos não autorizados sem bloquear operações legítimas.

- Preservar os relacionamentos.

- Informar erros de importação.

O professor solicita a evolução do sistema e recomenda dados de teste, mas não deixa totalmente explícito se a importação integral dos dados reais é obrigatória. Portanto, registre essa distinção na documentação.

### Critério para avançar

O seed deverá funcionar no ambiente de desenvolvimento. Se a importação for implementada, teste-a com cópias dos dados, sem comprometer os arquivos originais.

# REGRAS GERAIS DE EXECUÇÃO

Estas regras valem para todas as etapas:

1. Execute os passos na ordem indicada.
2. Não implemente funcionalidades de etapas futuras antes de estabelecer suas dependências, salvo quando uma adaptação for indispensável e estiver justificada.
3. Após cada passo, valide o resultado antes de continuar.
4. Se encontrar um erro, investigue a causa e corrija-o antes de avançar.
5. Não substitua o projeto inteiro por uma implementação genérica.
6. Não remova funcionalidades existentes sem necessidade.
7. Não invente regras de negócio, campos, permissões ou requisitos.
8. Evite dependências e abstrações desnecessárias.
9. Não utilize dados reais para testes destrutivos.
10. Não exponha segredos ou informações sensíveis.
11. Preserve a tipagem do TypeScript e evite o uso desnecessário de `any`.
12. Documente as decisões técnicas importantes.
13. Diferencie requisitos obrigatórios do enunciado de recomendações e melhorias opcionais.
14. Se encontrar uma ambiguidade que não impeça o trabalho, registre a premissa adotada e prossiga com a solução mais simples compatível.
15. Se encontrar uma ambiguidade que possa causar perda de dados, comprometer a segurança ou mudar significativamente o escopo, interrompa apenas a operação afetada e solicite esclarecimento.
